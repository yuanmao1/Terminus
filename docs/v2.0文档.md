版本策略调整：上述能力全部收敛到 Terminus 0.2.0，一次性发布，不再拆成 0.2.1/0.3.0。

但“一次发布”不等于“一次性并行堆功能”。请把 0.2.0 作为一个大版本项目，按内部里程碑串行实施；每个里程碑必须通过门禁后才能进入下一阶段。期间允许多个内部 commit、测试构建和本地 prerelease artifact，但不要提前 tag 或 npm publish。最终只有一个正式 tag `v0.2.0` 和一次 npm 发布。

0.2.0 的完整目标：

1. 统一 OperationAttempt + ReceiptEvent 不可变操作账本；
2. 每次远程调用都有 request_id 和可对账的结构化回执；
3. 真正恒定内存、支持 >2GiB、resume、双端 SHA、no-clobber、原子发布的 stream push；
4. binary-safe stdin、输入字节数/SHA 回执、输出流式上限；
5. 独立远端 supervisor，提供 PID/PGID、双 deadline、TERM→KILL、取消、查询和 reconcile；
6. `completed / failed / timed_out / cancelled / indeterminate` 等真实终态；
7. 多消费者 cursor 与独立 probe cursor；
8. 持久化 progress、businessResult、phase 和 terminal receipt；
9. 不可变 job attempt 与 `job inspect/receipt`；
10. 生命周期 Lease、稳定 owner、自动续租、takeover 审计；
11. memory freshness，以及受信任边界明确的 verify_cmd；
12. 完整 handoff，聚合账本、job、transfer checkpoint、lease、memory 和错误；
13. `--argv-json`、`--shell none|bash|zsh|powershell`；
14. 原生 audit 模式；
15. Docker/service 结构化 inspect 与 health wait；
16. fail-stop PlanRun/PhaseAttempt 工作流；
17. 不导出私钥的 pinned stdio tunnel。

内部实施顺序：

M0：冻结架构合同

先输出并由程序员确认：

- OperationAttempt 状态机；
- ReceiptEvent schema；
- remote helper 的安装、升级和兼容模型；
- indeterminate 是否阻止同 scope 后续 mutation；
- Lease 生命周期和冲突矩阵；
- host-key pin 的首次信任、轮换、撤销规则；
- audit allowlist 与远端受限 helper 的安全边界；
- Plan mutation approval 和 reconciliation 语义；
- sensitive data 的落库、脱敏、保留和导出规则。

这些都是 B 类决策。在确认前不要开始 schema 或实现。

推荐架构：使用受限 remote helper 作为 supervisor 和通用字节流端点；普通 shell wrapper 可作为 capability 明确、功能受限的兼容模式，但不得伪装拥有 PID/PGID 证明、binary framing、强 timeout 或 audit 隔离能力。

M1：持久化底座

实现：

- 并发安全的 migration runner：取得 SQLite 写锁后重新读取 user_version；
- operations；
- operation_events；
- transfer_checkpoints；
- job_attempts；
- leases；
- plan_runs / phase_attempts；
- host_pins 或等价可信 pin 存储；
- 必要的 retention/redaction metadata。

一次 npm 发布可以包含多个 append-only schema migration，例如 v5、v6、v7；不要为了“版本号是 0.2.0”把全部 SQL 塞进一个不可审查的大 migration。旧 migration 冻结不改。

每个 migration 都必须支持：

- fresh DB；
- 从所有历史版本顺序升级；
- 重复 reopen；
- 事务失败回滚；
- 两个进程并发首次打开；
- 历史数据完整性 readback。

M2：统一远端执行与 receipt

先打通最小纵向链路：

submit → connect → remote helper receive → remote_started(pid/pgid) → output stream → terminal receipt → query/reconcile。

任何 transport 断开都不能猜测结果。证据不足进入 indeterminate。

必须先让 exec/run/job 全部复用该链路，禁止每个命令各写一套状态机。

M3：ByteStream 与 ArtifactTransfer

实现：

- stream push；
- binary stdin；
- stdout/stderr 有背压流式读取；
- byte count、SHA-256、速率、ETA；
- checkpoint/resume；
- remote partial；
- no-clobber 原子提交；
- 双端校验；
- HTTP fetch 复用同一 ArtifactTransfer receipt/checkpoint 模型；
- pinned stdio tunnel 复用同一 ByteStream，但不得绕过 host pin 验证。

M4：Job、Progress、Lease、Memory、Handoff

实现：

- 输出 consumer cursor 与状态 probe cursor 分离；
- marker 跨窗口解析；
- progress/businessResult 持久化；
- 不可变 job attempt；
- 生命周期 Lease 自动续租；
- takeover/force/release 审计；
- memory freshness；
- verify_cmd 默认 untrusted，导入后未经显式信任不得执行；
- handoff 输出 `schemaVersion/complete/errors/source/observedAt/resume argv`。

M5：Typed Invocation、Audit、Inspect、Plan

实现：

- argv-json；
- shell none 和显式 shell；
- secret 参数不落明文；
- audit 通过受限 helper、命令 allowlist、sudo policy 和只读 wrapper 建立边界；
- Docker/service inspect 只是 Typed Invocation adapter，不得形成独立执行模型；
- PlanRun 只编排 OperationAttempt；
- phase 独立 receipt；
- 上一步未成功，下一步绝不提交；
- mutation 前必须批准；
- indeterminate 必须停在 reconciliation；
- 不自动重试；
- 补偿仅显式执行。

M6：全量验证与唯一一次发布

本地门禁：

- 单元、状态机、JSON golden；
- migration 多版本与并发；
- receipt 并发终态唯一性；
- redaction/secret 泄漏负向测试；
- daemon fresh-start 管道 EOF；
- Windows PowerShell argv/binary/CRLF 边界。

受控故障测试：

- >2GiB 流式传输及峰值内存；
- 任意 offset 断线和 resume；
- 本地源文件变化、远端 partial 污染；
- no-clobber 并发竞争；
- hash 错误、磁盘满、rename 失败；
- 提交前、提交后、启动后、完成后响应丢失；
- TERM、KILL 和无法确认存活；
- progress 超过 1MiB和跨窗口；
- Lease 超时、续租失败、takeover；
- audit 禁止项绕过尝试；
- host-key 不匹配和 pin 轮换；
- Plan phase failed/timed_out/indeterminate 后确认后续 mutation 未提交。

隔离远端 e2e 通过后，再执行：

ReleaseSafe build
→ 生成 npm tarball
→ 比对 tarball 内 exe SHA
→ 临时 prefix 安装
→ 完整 smoke
→ commit
→ tag v0.2.0
→ npm publish
→ 从 registry 全新安装复验。

发布阻断原则：

- 任一核心状态仍可能伪成功，不发布；
- receipt 与真实远端状态无法对账，不发布；
- stream push 仍整文件加载，不发布；
- timeout 后无法确认却返回普通 failed，不发布；
- secret 进入 snapshot、receipt、handoff 或日志，不发布；
- audit 仅靠本地字符串判断却宣称可信只读，不发布；
- host pin 未建立真实验证链，却宣称 pinned，不发布；
- Plan 在失败或 indeterminate 后仍可能提交下一 mutation，不发布。

如果完整 0.2.0 工作量过大，不允许通过降低语义、吞错、兼容 fallback 或弱化测试来赶发布；应停下来汇报具体阻断和剩余范围，由程序员决定是否缩减功能。未经程序员决定，不得自行拆版本，也不得发布“名义支持、实际不可靠”的半成品。
