## 零、执行期作出的破坏性决策（仓库里唯一的记录）

`docs/v2.0文档.md` 是 174 行的目标陈述，**没有破坏性变更清单也没有 B 类决策表**，所以这些决定只能记在这里。

**1. 撤销 CRLF 默认转换（`b1251e3`）。** 0.1.10 刚把 `--stdin` / `--cmd-file` 的 CRLF→LF 设为默认；现在关闭：
字节原样通过，`--normalize-lf` 显式开启，而输入含 CR 且未开规范化时在 stderr 和 JSON 各报告一次。
保住 0.1.10 真正的价值（让操作者**知道**有 `\r`），去掉危险的那半（静默改字节）。

范围是**命令文本，不含 `--stdin-file`**：在那里 `\r` 是数据，改写它会破坏载荷，并让回执的摘要描述一份不是该文件的字节。
`--stdin-file` 也不对 CR 告警——二进制里 `0x0D` 是常态，每份载荷都告警等于训练操作者忽略告警。

`--raw` 不再影响命令文本（它是旧的 opt-out），仍是 `read`/`write` 的真实 flag。

**2. 一处溯源更正，供以后引用时注意。** 我曾把 no-clobber 的 `ln` 处方引作 `docs/v2.0文档.md` §3.3，把 CRLF 撤销引作 §5.1。
**两者都不在那份文档里**——它没有节号结构。那些详细设计在仓库外的计划文件里，这也意味着**任何 subagent 都看不到它**。
仓库内的权威只有两份：`docs/v2.0文档.md`（目标）和这份台账（执行与决策）。

### 这条支线最后暴露的架构级问题（都已闭合）

1. **"一个销毁合同"是过度声明。** 存在两个:**claim-backed**(`commitDestruction`,持 lease,事务内重读自己的 claim)
   和 **quiescence-backed**(`servers.removeLocked`,不持任何东西,要求整台服务器无人持有任何东西)。
   后者更严,且把它折进前者需要为 server 级动作发明一个 lease。两者互不包含,现已各自命名。
2. **级联集合是隐式的。** `servers` 级联 **7** 张表(不是我先前 grep 出的 10——那是**有 `server_id` 列**的表数,
   其中 3 张是 `SET NULL`)。集合现在从**已应用的 schema** 推导并双向held,新增级联表会点名失败。
3. **两份手写"谁持 claim"清单彼此分叉。** `claim_reporting_bodies` 说 7 个,`claim_holding_bodies` 说 2 个,
   `reportFinishedDuringKill` 在前者不在后者——于是它续租、写终态,而两条续租规则都不看它。现已改为**推导**(函数体内有 `stillOurs(` 即持 claim),
   两份手写清单删除,只留计数;并加了反向不变量(动手的函数体必须也在发布清单里,否则 `ClaimHolderDoesNotReport`)。
4. **写终态前的续租无门禁。** 三处 `_ = stillOurs(...)`,删掉任一行测试全绿。规则不是邻接而是"续租之后不得有远端往返",
   且必须区分**裸结算**(`settleObserved(`,只凭 `authority`)与**合同背书**(走 `commitDestruction`,事务内重读)——
   否则 `removeSession` 那个最安全的站点会被判违规,规则只能被削弱。两侧计数 `(6,1)` 和 `(0,1)`,从合同背书降级为裸结算现在会双重失败。

### 判断为错误投入、明确不做的

**按文件拆 `cmd_job.zig`**（约 5,000 行生产码 + 2,200 行交错测试，60 个顶层函数）。
问题不在"都在一个文件里"，而在 `killJob`(680 行) 与 `removeJob`(545 行) 是同一个 12 步序列的两份，其中 4 行逐字节相同。

## 五、需要程序员决定的数据丢失语义（新增，均只报告未改行为）

1. **`server rm` 移走了守护私钥的那道 FK。** `servers.key_id REFERENCES keys(id)` 是 `NO ACTION`，
   所以有服务器引用某 key 时 `key rm` 会被**拒绝**。`server rm` 之后该 key 无人引用，而 `keys.remove` 是一句裸 `DELETE FROM keys`
   ——无事务、无屏障、无确认，材料不可再生。两条路径的消息都不提 keys。
   （更正我先前的说法：`server rm` **不**销毁私钥本身，风险是反向的。）
2. **`redaction_rules` 被 `server rm` 销毁，无屏障、无计数、无消息**，而它是**安全声明**（显式声明的 secret 位置，
   使脱敏不依赖模式猜测）。7 张级联表里唯一三重零保护的一张。
3. **已释放的 lease 历史随服务器消失且不被提及** —— 屏障数的是 claim，不是行。
4. **`host_pins` 不在级联里**（无 `server_id` 列，键是 `(host, port, key_type)`）。同 host:port 重建服务器会**继承** pin，
   所以风险是**过期 pin**而非盲信。当前零生产调用方，在 host-key 验证接上之前是惰性的。

## 七、纪律（已被这条支线反复验证过的）

- 改过 anchored 文件后跑 `python tools/mutate.py --check-anchors`；绿测试看不见死锚点
- 锚点唯一性必须程序化计数，不许肉眼
- 一个 mutation 若被编译器抓住，它什么都没证明——重新推导直到是门禁在失败
- 文档里的值/退出码若无门禁解析，就是无保护的；已因此漏过三次
- 匿名 `test {}` 也是一个 test：聚合器用 `comptime { _ = @import(…) }`，不用 `test {}`
- 每轮 mutation run 后 `.zig-cache` 涨约 7.5 GB；整个删掉，冷编译约 90 秒
- 只说"零 `CONNECTION_RESET`"，不说"零输出痕迹"——**当前有 7 行 `terminus:` 诊断是故意打印的**（5 个预期失败 + `b1251e3` 的两个提示，后者本身就是交付物）。这个数字每次新增故意打印的路径都要重数，不许沿用记忆里的旧值
- `zig build test` 输出里那一行 `failed command:` 是**既存**的：它是 Zig 回显产生了 stderr 的那个 runner，
  `git stash` 后在 HEAD 上同样出现一次，两边都 exit 0。不要把它当成失败，也不要当成自己引入的
- **`grep -c` 会把注释数进去。** 本轮我用 `grep -c "_ = stillOurs(...)"` 得到 3 就以为 mutation 没应用，
  其中一处是注释里的引用——树实际上是脏的。数"活的调用点"必须剥掉注释行，正是扫描器自己在防的错误
- **手写清单会分叉。** 同一个问题("谁持 claim")在一个文件里被回答两次，两份答案都对自己的问题成立而彼此不一致。
  能推导就推导（走树、读 schema、扫函数体），只留计数
- **但推导不能取消计数。** 推导的成员资格有一个失效模式：删掉某函数体最后一次续租，它就整个**掉出**集合，规则不再看它。
  抓住这一点的是那个被写下来的数字（3 → 2）
- 只说"非注释改动行为 0"这类话时要机械核验，别凭印象
- **一个锚点是两个会独立漂移的指针。** `find` 跟着代码，`expect_gate` 跟着测试名;改测试名只动后者。
  `--check-anchors` 现在两条轴都查（`2f61dc4`）。我在 `582f837` 改名时漏掉后者，让**全量 197 条自那时起不可能跑绿**，
  而唯一能发现它的方式是花掉那三十分钟
- **能挂死的测试比会失败的测试更糟。** `transport_test.zig` 的 socket stub 线程挂住整个套件，
  代价是每次运行一个超时,而且它把一个**真实的门禁失败藏了整整一个会话**。
  测试夹具里的线程必须由**性质**保证活不过它的测试，不能靠"客户端行为良好"
- **Python 在 Windows 上写文件默认把 `\n` 翻成 `\r\n`。** 写 `tools/mutations.json` 或任何源文件必须 `newline="\n"`。
  CRLF 进 `.zig` 会让 `Control.bodyOf` 直接失败，而 `.gitattributes` 把 diff 规范化掉——于是 runner 开始把
  真实的门禁失败归因给下一个跑到的 mutation（`mutate.py` 的 `apply()` 里记着这段历史）
- **"零调用方"和"未被检查"是两件事。** `refAllDecls` 非递归（`std/testing.zig:1213` 单层 `inline for`），
  而 Zig 惰性分析函数体，所以一个只被命名空间引用的 `pub fn` 的**函数体可能从未被语义分析过**。
  `d68fbdc` 用在 `createRun` 体内种 `comptime { @compileError(...) }` 而套件仍 409/409 通过实证了这一点
- **改名一个测试要连带搜 `expect_gate`；删代码要跑 `--check-anchors`；两者都不靠记性**

### 关于 golden 文件的决定（记录理由，因为它是一次"不做"）

文档要求 "JSON golden（旧字段继续存在、新字段版本化）"。**没有做 golden 文件**，理由：键集门禁已经抓住改名、删除、重排和数量；它看不见的是**嵌套深度**和**封闭词表**——而这棵树已为这个盲点付过十八个提交的代价（一个断言在错的深度匹配 `status`，一直通过）。而 golden **文件**会额外带来一个重新生成的仪式，**把漂移变成一次按键的橡皮图章**。所以只做键集看不见的那两样，别的不做。

同时补上了十三道键集门禁底下那个此前只对**一个**结构生效的前提：一道门禁覆盖 6 个模块、13 个结构、173 个字段，其中三个 `pub` 的逐字段名对 `@typeInfo` 交叉核对，**所以扫描器是被编译器验证过的而不是被信任的**。
